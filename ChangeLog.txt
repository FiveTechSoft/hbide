2026-10-25
----------

  Editor de codigo (rama editor-fixes, sin merge)
  -----------------------------------------------
  - Corregido: hotkeys de Alert muertos con opciones "&Save"/... (071f368);
    hb_gt_def_Alert compara la tecla con el primer caracter de la opcion,
    que con '&' es el propio '&'. Opciones sin '&'
  - Corregido: marcos 'oooo'/'cccc' en modo UTF8 (d8eb435); hb_DispBox
    parsea con el BOXCP del GT y el frame se generaba con hb_UTF8ToStr
    (CP anfitrion). hb_UTF8ToStrBox en HelpView y Compiler Flags
  - Help "Welcome": ya no afirma que Alt+letra no abre menus en Linux
    (31c1b6f)
  - Matriz completa del IDE verificada en vivo (File/Edit/Run/Options/Help,
    Alerts, UTF-8). Checkpoint completo, pruebas y limitaciones:
    docs/editor-checkpoint-2026-10-25.md
  - Nuevo: comentarios de bloque /* */ multilinea coloreados, con cache
    incremental por linea (invalidacion desde la primera linea editada;
    cadenas con /* dentro y comentarios // respetados). Primera version
    (3cab730) con fallo de reanudacion del cache; corregido en 926c109.
    Coste del escaner aislado (microbenchmark, NO end-to-end): 108 ms
    peor caso sobre 20.000 lineas; en uso real no hay demora perceptible
    al saltar a la linea 19990 ni al recolorear tras editar la linea 3
  - Estetica: mensajes del IDE ya no usan el Alert rojo del GT; nuevo
    HBIDE_MsgAlert() con dialogo blanco y botones verdes con sombra
    (estilo Turbo Vision): confirmacion de guardar/descartar, archivo
    no encontrado, resultados de reemplazo y compilacion, etc.
    Activacion por hotkey, Enter o Espacio
  - Corregido: resaltado fantasma de la linea actual tras saltos de mas
    de una linea (Ctrl+Home/End, Undo/Redo); la linea previa se repinta

  Construccion de EXEs desde el IDE (Run>Start) y correcciones
  ------------------------------------------------------------
  - Corregido: con el fuente abierto por ruta completa, el build era
    bueno pero el IDE comprobaba File() sobre ".//ruta/absoluta" y
    mostraba "Build failed" (cb418dc); ahora busca el exe por nombre base
  - Corregido: la salida de hbmk2 en el dialogo mostraba glyphs (CR de
    progreso); ahora se traducen a saltos de linea (cb418dc)
  - Corregido: un binario viejo del mismo nombre podia sobrevivir a un
    build fallido y confundir la comprobacion/ejecucion; Run>Start borra
    el exe previo ANTES de compilar y genera la salida con -o junto al
    fuente, asi dos fuentes con el mismo basename en directorios
    distintos no colisionan (808c45c)
  - Verificado en vivo (pty gttrm, Linux): exe ELF real construido y
    ejecutado ("hola desde exe", EXIT 0) con autorun desde el IDE; error
    de compilador legible; binario viejo borrado y nunca ejecutado tras
    el fallo (alerta "Build failed" correcta); mismo basename en otro
    directorio genera y ejecuta su propio exe ("from exedir"), no el del
    CWD.
  - Corregido (Windows): hbmk2 en Windows no acepta -comp=gcc (id de
    hosts unix), asi que Run>Start fallaba siempre con el default "GCC";
    nuevo valor "MinGW64" en Compiler Options y default por plataforma
    (HBIDE_DefCompiler(): MinGW64 en Windows, GCC en unix)
  - Verificado en vivo Windows via Wine 5.5 + Xvfb (cadena Windows
    completa, sin Linux en el build): hbide.exe PE32+ cross-compilado
    abre el IDE completo; File>Open y edicion reciben teclado;
    Run>Start construye wedit.exe PE32+ desde el IDE con hbmk2.exe +
    harbour.exe + gcc.exe de Windows (winlibs mingw64 en el PATH del
    prefijo). Notas: (1) el default "Strict types" (-es2) convierte en
    fatal el warning W0001 (p.ej. variable de bucle for sin local):
    mismo comportamiento que en Linux; (2) Wine 11.x no arranca en este
    sandbox (CommitLimit ~991MB vs reserva de ntdll); Wine 5.5 amd64 si
    - limitacion del entorno de pruebas, no de hbide

  Debugger Harbour integrado (Run>Debug): verificacion en vivo
  ------------------------------------------------------------
  - El debugger ya estaba integrado (hbdebug/ vendored en hbide.hbp);
    Run>Debug compila el buffer a un .hrb unico y entra con vista de
    fuente y ventana Command
  - Verificado en vivo (pty gttrm, Linux): BP con F9 sobre la linea del
    cursor del code window (marca roja; "list bp" lo confirma), Go F5 con
    parada en el BP, ToCursor F7 (parada en la linea del cursor con las
    variables ya actualizadas), Step F8 (ENTRA en funciones: de la
    llamada a AddNum salta a su primera linea), Trace F10 (ejecuta la
    llamada completa y para en la siguiente linea del nivel actual;
    convencion historica del debugger de Harbour: hb_dbgSetTrace arma
    bTraceOver = trace-over), consulta de variables con ? (0 -> 1 -> 15),
    salida del programa visible ("total:         15"), Alt+X vuelve al
    editor con el buffer intacto y el debugger se puede reabrir
  - Nota UX: el cursor del code window arranca en la linea de ejecucion
    actual (no en la linea 1); F9 sin mover el cursor crea el BP ahi
  - Corregido (Windows): Run>Debug fallaba con "Open error" al generar
    el nombre unico del .hrb temporal: hb_MilliSeconds() en Windows es
    uptime (GetTickCount), no ms desde medianoche, y en maquinas con
    mucho uptime desborda el Str(...,15,3) produciendo asteriscos -
    nombre invalido en Windows (CreateFile STATUS_OBJECT_NAME_INVALID,
    diagnosticado con traza WINEDEBUG=+file bajo Wine). Ahora se usa
    hb_MilliSeconds() % 1000000 con Str(...,10,3)
  - Verificado en vivo Windows via Wine 5.5 + Xvfb: Run>Debug abre el
    debugger completo (ventana de codigo con el fuente transformado
    Main->__Main + init __hbide_debug__, ventana Command), el programa
    corre y se vuelve al editor con el buffer intacto
  - Verificado en vivo Windows via Wine: parada en breakpoint y
    evaluacion de variables - comando "bp 4" en la ventana Command, Go
    F5 para en la linea 4 (for), ? n devuelve NIL (aun sin asignar,
    correcto), Trace F10 avanza a la linea 5 y ? n devuelve 1
  - Pendiente (alcance ampliado 2026-10-25): revisar todas las funciones
    y opciones del debugger de Harbour y exponerlas desde el IDE
